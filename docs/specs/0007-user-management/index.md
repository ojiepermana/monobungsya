# 0007. User lifecycle management in the user service

**Date**: 2026-08-22 · Updated: 2026-08-24
**Status**: Accepted

## Summary

The user service grows from a stub into the real owner of the user domain. Admins can create and update users, suspend, block, soft delete, and restore them, and every action leaves an audit trail with a reason. Users are never hard deleted; a `deleted_at` timestamp marks a retired account while its history stays intact. The web app gets a `/users` list page and a `/users/:id` detail page showing the profile plus that user's audit, access, and application logs, and the user id is generated by the Angular client as a UUIDv7 and sent with the create request.

Updated 2026-08-24: both web pages compose the shared page scaffold from `@ojiepermana/angular/theme/page` (the stacked variant with the header, filter, content, and footer slots) instead of a hand rolled `<main>` layout, matching the web UI standard and the package showcase. The user list filter is closed by default and opens from the `Filter` toggle in `PageHeader`. Primary header actions and table row actions use compact `xs` buttons. The recomposition and its interaction coverage now pass alongside AC-1 through AC-11, closing AC-12.

> **Superseded authorization note, 2026-08-24:** role input, role updates, the last admin role guard, role based route access, and role fields in the original AC-1, AC-3, AC-6, AC-8, data model, API, and value sourcing tables were replaced by the permission first model in [spec 0008](../0008-permission-acl/index.md). User lifecycle, status transitions, invitation, audit, list, detail, and page composition decisions remain active. Current user administration requires `user:user:manage`, while grants are managed by the access service.

## Requirements

**User stories**:
- As an admin, I want to create and update users so that new people can log in with the right role.
- As an admin, I want to suspend, block, soft delete, and restore users so that access can be removed and given back without losing history.
- As an admin, I want a user detail page with the profile and that user's logs so that I can see who they are and what they did.

**Acceptance criteria** (the contract, each independently checkable):
- **AC-1**: An admin can create a user by sending id (a client generated UUIDv7), name, email, and role. The user appears in the list and can log in through the existing magic link flow. A duplicate id or a duplicate email each return 409 with a distinct error code.
- **AC-2**: After a successful create, the user service publishes a `user.invited` event and the auth service sends the new user an invitation magic link email. When infrastructure is disabled or NATS is unavailable, the create still succeeds and the skipped invitation is logged as a warning.
- **AC-3**: An admin can update a user's name and role. Email cannot be changed through the API. The update is audit trailed with before and after state.
- **AC-4**: An admin can suspend, unsuspend, block, and unblock a user, each with a mandatory reason. A suspended or blocked user cannot request a magic link, cannot complete any login, and their active sessions stop working on the next request.
- **AC-5**: An admin can soft delete a user (sets `deleted_at`, the row is never removed) and restore them. A deleted user cannot log in, is hidden from the default list, and is reachable through the status filter. Email stays unique across all users, including deleted ones.
- **AC-6**: Status actions against the caller's own account are rejected, and the last remaining active admin cannot be suspended, blocked, deleted, or moved off the admin role.
- **AC-7**: Every mutation writes an audit trail entry through ActivityLog (action, actor from the verified identity, reason where required, before and after state). A failed audit write fails the request.
- **AC-8**: All user management endpoints require the admin role. Any other role receives 403 at the gateway.
- **AC-9**: The web app has a `/users` list page (search, status filter, paging, status badges, create dialog, row actions) and a `/users/:id` detail page (profile card with derived status, timestamps, action buttons, and three log tabs). The old user access settings list is replaced by these pages.
- **AC-10**: The three logs endpoints accept an optional `actorUserId` filter and the detail page tabs show only that user's logs, with paging.
- **AC-11**: List and management endpoints live in the user service behind `/api/v1/users`. The `/api/v1/auth/users` route and the auth service list code are removed, and the auth service keeps only the read only login checks, extended to `blocked_at` and `deleted_at`.
- **AC-12** (added 2026-08-23): Both web pages compose `Page` from `@ojiepermana/angular/theme/page` with `variant="stacked"` and `scroll="content"`: a `PageHeader` (title and primary action), a `PageContent` (states, table or cards, tabs, and the dialogs), and a `PageFooter` (paging controls) on both pages, plus a `PageFilter` with `placement="stacked"` on the list page. The list filter is `collapsible`, closed by default, and opened or closed by the `Filter` toggle in `PageHeader`; its search, status filter, and clear action remain available when open. Header primary actions and table row actions use `Button` with `size="xs"`. The slots render unconditionally, no page level `<main>` remains, exactly one `role="main"` landmark exists per screen, and only the content region scrolls while header, filter, and footer stay pinned.

## Decision

**Chosen option**: Option 1: full ownership in the user service, statuses as timestamp columns.

The user service owns every read and write of the user domain (list, detail, create, update, all status actions), while the auth service keeps only the read only checks that login needs. Status is stored as three nullable timestamps (`suspended_at` existing, `blocked_at` and `deleted_at` new) and the effective status is derived with the precedence deleted, then blocked, then suspended, then active (basis: the existing `suspended_at` checks in the auth login queries, which this extends instead of rewriting).

Update 2026-08-23, page composition: the two web pages compose the package page scaffold, `Page` in the stacked variant with the header, filter, content, and footer slots, instead of the hand rolled `<main>` layout they shipped with. This was already the standing rule for every page (basis: spec `0010-angular-ui-standard`, AC-15), the showcase is the consumer contract for how the slots are assembled, and the hand rolled `<main>` duplicates the `role="main"` landmark the package layout wrapper already renders, which the same standard's browser checks forbid. The list filter follows the package's `collapsible` stacked behavior, starts closed, and is controlled by the `PageFilterToggle` in the page header. Page header actions and table row actions use the package button's `xs` size so dense page controls share one compact rhythm.

**Implementation skills**: `elysiajs` (personal skills, `~/.claude/skills/elysiajs/`) · `angular-developer` (personal skills, `~/.claude/skills/angular-developer/`). Read the `@ojiepermana/angular` showcase before composing the new pages; it is the reference for how that package's components are meant to be assembled.

## Feature design

**Data model** (the target; `user.users` is altered, no new table):

| Column | Type | Rule |
|---|---|---|
| id | uuid PK | supplied by the client as UUIDv7 on create; the DB default `uuidv7()` stays for seeds |
| role | varchar(50) not null | CHECK unchanged: admin, manager, bi, staff, legacy |
| name | varchar(255) not null | updatable |
| email | varchar(255) not null | UNIQUE across all rows including deleted; immutable through the API |
| email_verified_at | timestamptz null | unchanged |
| suspended_at | timestamptz null | existing |
| blocked_at | timestamptz null | **new** |
| deleted_at | timestamptz null | **new**, the soft delete marker |
| created_at | timestamptz not null | default now() |
| updated_at | timestamptz null | set on every mutation |

Existing relations stay unchanged: `auth.login_tokens`, `auth.sessions`, and `auth.passkey_credentials` reference `user.users(id)`; the logs tables point through `actor_user_id` without a foreign key (partitioned tables).

New event contract in `packages/contracts/src/events`: `user.invited` with payload `{ userId, email, name, requestedBy, occurredAt }`.

**State transitions** (derived status, precedence deleted, then blocked, then suspended, then active):
- suspend: allowed when active. unsuspend: allowed when suspended and neither blocked nor deleted.
- block: allowed when active or suspended (an escalation; `suspended_at` is not cleared). unblock: allowed when blocked and not deleted; the user returns to suspended when `suspended_at` is still set, otherwise to active.
- delete: allowed from any status except deleted; sets only `deleted_at`. restore: allowed when deleted; clears only `deleted_at`, so the user returns to the status they had before deletion.
- Any other action on a deleted user returns 409. A redundant transition (for example suspending an already suspended user) returns 409 rather than silently succeeding.

**API surface** (user service internal routes; the gateway maps `/api/v1/users/*` and forwards signed identity headers):

| Endpoint | Method | Key inputs | Key outputs | Auth | Key errors |
|---|---|---|---|---|---|
| /internal/users | GET | search, status (active, suspended, blocked, deleted, all), page | data[], meta, filter options | admin | 401, 403 |
| /internal/users/:id | GET | id | profile, derived status, all timestamps | admin | 404 |
| /internal/users | POST | id (uuid), name, email, role | created user | admin | 409 id taken, 409 email taken, 422 |
| /internal/users/:id | PATCH | name?, role? | updated user | admin | 404, 409 last admin downgrade, 422 |
| /internal/users/:id/suspend | POST | reason (required) | updated user | admin | 404, 409 invalid transition, self, or last admin |
| /internal/users/:id/unsuspend | POST | reason (required) | updated user | admin | 404, 409 |
| /internal/users/:id/block | POST | reason (required) | updated user | admin | 404, 409 |
| /internal/users/:id/unblock | POST | reason (required) | updated user | admin | 404, 409 |
| /internal/users/:id | DELETE | reason (required, body) | updated user | admin | 404, 409 self, last admin, or already deleted |
| /internal/users/:id/restore | POST | reason (required) | updated user | admin | 404, 409 not deleted |
| /internal/logs/audit-trails, access-logs, application-logs | GET | adds optional actorUserId (uuid) | rows filtered to that actor | unchanged | 422 |

Web routes: `/users` (list, with the create dialog) and `/users/:id` (detail).

**Page composition (web)** (added 2026-08-23; the consumer contract is the package showcase: `src/app/ui/theme/pages/pages.page.ts` for the slots and filter, `src/app/home-page.ts` for a page inside the shell):

Both pages are routed components with host class `block h-full min-h-0` whose template root is `Page` from `@ojiepermana/angular/theme/page`, replacing the hand rolled `<main>` scaffold. Shared inputs: `variant="stacked"` (the stacked slot layout), `scroll="content"` (the content slot is the only scroll owner and gets `tabindex="0"` from the package for keyboard scrolling), `height` left at its `auto` default (slots keep natural height; the host class chain already provides the frame, and `height="fix"` would clamp the header to `h-12`), and `[appearance]` bound to the live layout appearance axis so the page's section borders follow the shell setting.

| Slot | `/users` list | `/users/:id` detail |
|---|---|---|
| `PageHeader` | eyebrow, title, and the "Tambah User" button | eyebrow, the user's name, and the back link |
| `PageFilter` (`placement="stacked"`, `collapsible`, closed by default) | search input, status select, clear filters button, opened by the `Filter` toggle in `PageHeader` | not used |
| `PageContent` | error alert, loading and empty states, the user table, and all three dialogs | error, loading, and not found states, the profile card with action buttons, the log tabs, and both dialogs |
| `PageFooter` | page label and the four paging buttons | the active tab's page label and paging buttons |

Composition rules (they exist because `Page` projects only known slot selectors, with no catch all):
- The four slots render unconditionally; loading, error, and empty conditionals live inside a slot, never around it (selector based projection does not see through an `@if` block).
- Dialogs sit at the end of `PageContent`; markup outside a known slot selector is silently never rendered.
- No `<main>` element remains in either page template: the layout wrapper's content region already carries the single `role="main"` landmark, so a page level `<main>` duplicates it.
- The list filter is hidden initially and changes only through the `PageFilterToggle` in the page header. Header primary actions and table row actions use `Button size="xs"`.

**Value sourcing** (every produced or displayed value names its source):

| Action | Value | Source |
|---|---|---|
| create | id | input param, generated in Angular with the `uuid` package v7 function |
| create | role options in the form | the role CHECK list, exposed through the Elysia schema and the generated SDK types |
| every mutation | audit actor (id, name, email, role) | gateway identity headers verified by the user service `shared/plugins/auth-identity.plugin.ts` |
| status actions, delete, restore | reason | required body field, written to `logs.audit_trails.reason` |
| list, detail | derived status | computed from `suspended_at`, `blocked_at`, `deleted_at` with the stated precedence |
| invitation email | recipient email and name | the `user.invited` event payload, taken from the create input |
| invitation email | magic link base URL | `PUBLIC_API_URL`, decided in spec 0003 |
| last admin guard | count of active admins | repository count of rows with role admin and all three status timestamps null, run inside the mutation's transaction |
| detail page log tabs | log rows for this user | the three logs endpoints called with actorUserId equal to the route id |
| list | page size | fixed 25 per page, matching the logs pages |
| both pages | page `appearance` | `LayoutService.appearance()` from `@ojiepermana/angular/theme/layout/services`, the axis the settings surface updates |

**Key invariants**:
- No code path ever issues a SQL DELETE against `user.users`; retirement is only ever `deleted_at`.
- Email is unique across all rows including deleted ones, so restore can never collide.
- Magic link issuance, token consumption, and session validation all require the three status timestamps to be null (extends the existing `suspended_at` checks in the auth repository).
- When `deleted_at` is set, restore is the only allowed action.
- At least one admin with all three timestamps null always exists; the guard runs inside `withTransaction` together with the mutation.
- `ActivityLog.writeAudit` is awaited and its failure aborts the mutation, matching the log subsystem contract.
- All filtering and sorting goes through repository field whitelists; id is validated as a uuid before any query.
- The two user pages compose the package page scaffold only: no page level `<main>` and no hand rolled header, filter, or footer scaffolding exists under `apps/web/src/app/pages/users/`.

**Security model**: every `/api/v1/users` route requires a valid session plus the admin role, enforced at the gateway with the same capability check the old auth users route used, and verified again inside the user service through the identity plugin. The `actorUserId` filter rides the existing logs permissions. No new compliance scope; name and email were already stored.

**Configuration required**: none new. The NATS subject for `user.invited` is a constant in `packages/contracts`.

**Critical test scenarios**:
- Happy path: create with a client UUIDv7, the list shows the user, magic link login works, verifies **AC-1**.
- Duplicate id and duplicate email each return 409 with distinct codes, verifies **AC-1**.
- Suspend with a reason kills an existing session on the next request and blocks magic link issuance, verifies **AC-4**.
- Delete then restore a previously suspended user returns them to suspended, verifies **AC-5**.
- Self suspend and last admin delete both return 409, verifies **AC-6**.
- A non admin role receives 403 on every `/api/v1/users` route, verifies **AC-8**.
- The actorUserId filter returns only that user's rows in all three log endpoints, verifies **AC-10**.
- A failing audit write rolls the mutation back, verifies **AC-7**.
- With NATS off, create succeeds and logs a warning instead of publishing, verifies **AC-2**.
- Composition: both pages render the package slots (a closed by default, toggleable filter on the list only), exactly one `role="main"` landmark exists per screen, header and table actions use `xs`, and only the content region scrolls while header, filter, and footer stay pinned, verifies **AC-12**.

## Migration plan

**Strategy**: single release cutover, no data transformation.
**Phases**: the two new columns are nullable adds, safe on a running database; the code and endpoint moves ship in the same release since every app deploys from one repo.
**Rollback**: revert the commit; the added columns are harmless if left in place.
**Risks**: the web client and the removed auth users endpoint must switch together, which step 7 guarantees by removing only after the new pages are live; a missing grant for the user service role would surface as a 500 on the first list call, which step 2's verification catches early.

## Consequences

**Positive**:
- The user domain finally lives in the service named for it, keeping every service extractable to its own repo unchanged.
- Retired accounts keep their full history, and the logs correlation makes the detail page a real investigation tool.
- The timestamp status model reuses the existing login checks, so the auth changes are additive and small.
- The recomposed pages get the pinned header, filter, and footer plus the single main landmark from the package, removing a live duplicate `role="main"` and bringing the pages under the web UI standard's page contract.

**Negative / tradeoffs**:
- The auth service still reads `user.users` directly (a cross schema read). Acceptable while both share one database, but it is the coupling to revisit if the services ever get separate databases.
- Deleted users lock their email forever; a returning person needs a new address or a manual database change.
- Explicit 409s on redundant transitions mean the UI must refresh state after a failure instead of relying on retries that quietly succeed.
- A client generated id makes id untrusted input everywhere: the server must always validate the format and handle collisions.
- The pages are now coupled to the package page slot contract, and slot projection fails silently: markup outside a known slot selector simply never renders, so the page tests must assert the composition, not only the data.

**Neutral**:
- Restore semantics depend on preserved timestamps, so nothing may "clean up" `suspended_at` or `blocked_at` on deleted users.
- The user service keeps its stub status module beside the new users module.
